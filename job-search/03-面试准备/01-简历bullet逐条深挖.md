# 面试准备 · 01-简历bullet逐条深挖

每条格式: 原文 → 讲解(30-60秒) → 追问预判 → 证据 → 兜底。**所有数字必须先自己确认口径, 说不清就要改简历。**

## 项目一 · 多语言代码图谱引擎 + MCP 服务

### B1. 多语言静态解析引擎（Clang AST / Jedi / LSP → tree-sitter + LSP Go 重写, 73/73）

- **讲解**: 背景是 AI Agent 要回答代码问题, 传统检索给不了"函数调用链/依赖关系"这类结构化事实。第一版 Python 用 Clang AST(C/C++)、Jedi(Python)、LSP(Java) 三个解析器; 后来用 Go 重写, 核心是 tree-sitter(语法树)+LSP(工程语义, 如 Java 的类层级), 兼容四语言。两版语义逐字段对齐, 用验收 harness 73 个用例对比, 73 个全过, 保证重写后行为不变。
- **追问预判**:
  - 为什么用 Go 重写?（性能? 分发易部署? 我当时的具体动机）
  - tree-sitter 和 AST 的区别? 为什么要 LSP 补语义?（Java/C++ 靠 AST 拿不到跨文件的类型信息）
  - 73 个用例怎么设计的?（每个语言*每种查询类型的矩阵?）
  - 增量还是全量解析? 大仓库怎么办?（性能兜底: 按文件分片/缓存）
- **证据**: Clang AST、Jedi、LSP、tree-sitter 选型; 验收 harness 文件与 73 用例; 四语言语义对齐表
- **兜底**: 说不清某语言细节就说"该语言部分由 LangSpec 规格+对应解析器处理, 我负责的是框架与对齐", 不硬编
- **风险**: 「四语言引擎」会不会被问"是不是只做了 Python 版再包装"? → 讲 Go 重写动机与对齐方法论

### B2. LangSpec 框架 + Graph Buffer + CBM 置信链 / MRO

- **讲解**: 多语言解析最难的是语义一致性——各语言 AST 结构不同。LangSpec = 语言无关的遍历器 + 每语言一份特化规格（函数定义/调用/类的识别规则）; Graph Buffer 负责跨文件合并: 边去重、节点确定性排序(保证输出稳定, 可复现); CBM 置信链与 MRO 解决多继承/方法解析的准确性（Python MRO、Java/C++ 多继承场景, 给"哪个方法的调用实际解析到哪个实现"标注置信度）。
- **追问预判**:
  - 确定性去重为什么重要?（Agent 检索输出可复现, 避免缓存不一致——这是我的设计判断）
  - 置信链怎么建模?（规则打分? 文本相似度? 多信号融合?）
  - 有没有误判案例, 怎么处理的
- **证据**: LangSpec 规格文件、Graph Buffer 去重算法、CBM/MRO 文档与测试
- **兜底**: 如果具体建模细节记不清, 说"算法是我与同事一起定型的, 我负责 X 部分", 并给出一个真实案例
- **风险**: 这些名词信息密度高, 若被问"为什么这么命名/为什么这么设计"要能讲出取舍（宁可诚实说"简化版本", 不吹）

### B3. MCP 服务 9 个工具

- **讲解**: MCP = Model Context Protocol, 给大模型提供标准化工具调用接口。我设计了 9 个工具: search_code / get_file_dependencies / search_error_log / list_external_calls 等。工具设计要点: 输入输出 Schema 化、按代码事实返回（不靠模型猜测）、错误日志定位元数据直接挂到代码节点。这样前端 Agent 可以"按图索骥", 而不是让模型自己搜。
- **追问预判**:
  - MCP 和普通 API 的区别?（协议标准化/工具发现/上下文传递——答 MCP 本质是 Agent 工具协议）
  - 每个工具返回什么? 数据结构多大? 截断策略?（上下文窗口限制——这是真实工程问题）
  - 工具权限与安全边界?（内网可信环境怎么处理）
  - 为什么 9 个, 怎么扩展?
- **证据**: MCP 工具定义文件、示例调用、与 Agent(如 Claude/Codex) 联调的日志
- **兜底**: 具体工具清单记不全时, 念 3 个最熟的 + "其余是依赖/错误定位类"
- **风险**: MCP 是当前热点, 面试官可能深挖协议细节(如 streamable HTTP、工具描述 token 优化)——提前补概念课

### B4. Agent 驱动研发: 134 commits / 1 个月 / 5 仓 CI/CD / 82% coverage

- **讲解**: 这是"用 Agent 做工程"的实践: 我以 Claude Code/Codex 为主力, 自己分解任务、写规格、验收; 1 个月从 initial commit 到生产级, 134 commits/132 issues(任务闭环率)。配套一次性建成 5 仓 CI/CD: 双平台构建矩阵(win/mac/linux)、pre-push 门禁、PyInstaller 打包。架构上做深层模块化: port 抽象(实现与协议解耦)、server 主体瘦身到约 100 行; 101+ 单测、624+ 用例、coverage 不低于 82%。
- **追问预判**:
  - Agent 写的代码你怎么保证质量?（我的做法: 验收 harness 一条条跑 + code review + 把 82% coverage 作为门禁——**这是关键答案, 必背**）
  - Agent 在哪类任务好使、哪类翻车?（failure mode: 大重构/跨文件一致性/需求模糊时崩, 这是真实体感, 腾讯 JD 要的就是这个）
  - 一天多少 commit? 怎么拆分任务?（利用 issue 闭环）
  - 为什么 coverage 82% 而不是更高?（体感: 边界处理类代码性价比低——真实取舍）
- **证据**: 仓库 commit 记录(可展示)、CI 配置、coverage 报告
- **兜底**: 不记得细节就说"记录都在仓库里, 我可以展示"
- **风险**: 面试官会怀疑"134 commits 是不是 Agent 乱刷"? → 用"132 issues 闭环+门禁+验收 harness"锁定语义

### B5. CMC 数据同步平台(SQLite→PostgreSQL+Alembic, -54.5%/-45.9%)

- **讲解**: 从 0 到 1 建数据同步平台: 全链路异步化、SQLite 迁 PostgreSQL(带 Alembic 版本化迁移)、ETL 增量同步。效果: 同步耗时 -54.5%、回拉接口 -45.9%。这是个偏数据工程的故事, 支撑"我把数据管道做扎实"的完整性。
- **追问预判**:
  - 增量同步用什么方案?（binlog/轮询/时间戳——如实回答）
  - 异步化怎么保证一致性?（补偿/重试/幂等）
  - -54.5% 怎么测的? 口径是什么
- **证据**: 迁移脚本、Alembic 版本、ETL 作业、监控数据
- **兜底**: 强依赖细节就问什么答什么, 不知道直接说"这部分的方案是团队定的, 我负责实现与联调"
- **风险**: 这条与主线(Agent)关系弱, 若面试时间紧可压缩为"配套数据管道"

## 项目二 · FaultPro（RAG + eBPF 故障诊断）

### B6. RAG 故障知识库（清洗→向量检索→精排）

- **讲解**: 设备故障日志/手册/工单进知识库: 清洗(去噪/切分/元数据标注)→向量化(Embedding)+语义检索→精排(重排序模型)全链路。用 RAG 的目的是让诊断 Agent 先检索再回答, 而非让模型死记。
- **追问预判**:
  - 检索怎么优化?（chunk 策略/混合检索/精排模型——**必补: hybrid retrieval 概念**）
  - 召回率怎么评估?（评测集+标注）
  - 和项目一的关系?（故障日志→代码图谱匹配→故障传播链）
- **证据**: 全链路代码、知识库样例、评测结果
- **兜底**: 若精排细节是团队定的, 讲清楚自己在哪一环
- **风险**: RAG 是 JD 高频词, 面试官必问, 概念课要硬补(Embedding/向量库/chunk/rerank)

### B7. eBPF 慢 IO 定界（<2% 开销）

- **讲解**: eBPF 无侵入式追踪 IO 路径: VFS→IO 调度器→NFS 网络时延分段, 定位慢 IO 到底慢在哪一段(本地磁盘? 网络?); 采集开销 <2%(通过采样/只挂关键 hook 控制)。这是观测能力, 与"Agent 可观测性"话题可迁移。
- **追问预判**:
  - eBPF 为什么开销低?（内核态挂钩, 用户态聚合）
  - <2% 怎么测的?（压测对比）
  - 和 observability 的关系?（Agent tracing 的类比: 我做过系统级观测, 理解 tracing 用什么）
- **证据**: 工具代码、时延分段统计图、测开销的实验方法
- **兜底**: eBPF 细节深挖答不出就回"我用的是基于 X 的开源框架, 实现的是 Y 层"
- **风险**: toolchain 细节很可能被深挖, 提前准备 vfs 层面 hook/printf 到用户态的方式

### B8. 日志解析适配器体系（ASan 栈/GCC 后缀名/pc:lr: 栈帧）

- **讲解**: RTOS/数据库/内核日志格式完全不同, 我做统一适配器层: 每种格式一个解析器(ASan 调用栈提取、GCC 符号后缀反解、pc:/lr: 寄存器栈帧识别), 输出统一结构化事件, 喂给后续故障链推理。
- **追问预判**: 适配器怎么扩展? 解析失败怎么降级?
- **证据**: 适配器代码、日志样例
- **兜底**: 具体正则/解析细节可略, 讲清抽象与统一 schema 即可
- **风险**: 无重大风险; 此条突出"工程落地能力"

### B9. opencode 批量诊断 Agent 工作流

- **讲解**: 用 opencode 搭批量诊断 Agent: 超时续跑(断点续跑, 不浪费多次重试)、部分输出复用(已完成子任务的结果缓存复用), 集成国产 AI 算力诊断工具。闭环: 日志诊断→故障链建立→知识库沉淀。
- **追问预判**: 为什么用 opencode 不用别家? 超时续跑怎么实现的?(状态持久化+幂等) 产出质量怎么控?
- **证据**: 工作流脚本、状态文件、复用品率
- **兜底**: 说"off-the-shelf 工具+工程化包装", 别把自己包装成框架作者
- **风险**: 面试官可能区分"你用 Agent 工具" vs "你造 Agent 工具"——诚实: 两者都有(项目一造基础设施, 项目二用工具)
